# f-37: Consumer-side Lifecycle Scripts (`prekley` / `postkley`)

- **Milestone:** M2
- **Complexity:** Medium
- **Depends On:** f-4 (push command), update/add/install commands (done)

## 1. Problem Statement

When `kley publish --push` (or `kley add` / `update` / `install`) changes a
managed package inside a consumer project, the consumer may need to react —
rebuild, regenerate code, restart a dev server, etc. There is currently no way
to hook into the update process automatically on the consumer side.

This is the counterpart to f-23 (publisher-side hooks). f-23 covers build steps
that run *in the library* during `kley publish`; this ticket covers scripts that
run *in the consumer project* when a kley-managed dependency is added/updated/
installed.

## 2. Proposed Solution

Consumer projects define lifecycle scripts in their `package.json`. Kley executes
them at specific points during the package lifecycle. This mirrors `yalc`'s
`preyalc` / `postyalc` scripts.

### Script Names

| Script | When it runs | Where |
|--------|-------------|-------|
| `prekley` | Before package files are updated | Consumer `package.json` |
| `postkley` | After package files are updated | Consumer `package.json` |
| `prekley.<pkg>` | Before specific package is updated | Consumer `package.json` |
| `postkley.<pkg>` | After specific package is updated | Consumer `package.json` |

### Execution Triggers

Scripts run in the **consumer project** when:

- `kley add <pkg>` — runs `postkley` / `postkley.<pkg>` after adding
- `kley update <pkg>` — runs `prekley` / `postkley` around the update
- `kley publish --push` — runs `prekley` / `postkley` in each consumer project during push
- `kley install <pkg>` — runs `postkley` / `postkley.<pkg>` after install

### Execution Order

For a push that updates `my-lib` in a consumer project:

1. `prekley`
2. `prekley.my-lib`
3. *(files are updated)*
4. `postkley.my-lib`
5. `postkley`

### Opt-in (safe by default)

Lifecycle scripts are **disabled by default** during `push`/`add`/`update`/
`install` to avoid unexpected side effects. The user opts in:

```bash
kley publish --push --scripts
kley add my-lib --scripts
kley update my-lib --scripts
```

The default can later be flipped in `.kleyrc` (see f-24).

### Error Handling (distinct from f-23)

Unlike publisher-side hooks (f-23, which abort `kley publish` on failure), a
failing consumer-side script during `push`/`update` should **log a warning but
not abort** the whole operation — a broken consumer hook must not block updates
to other projects in a multi-project push. (Revisit if experience shows otherwise.)

## 3. Usage Example

```json
// consumer project package.json
{
  "scripts": {
    "postkley": "npm run build",
    "postkley.my-ui-lib": "npm run generate:components"
  }
}
```

```bash
# Push with scripts enabled — consumer's postkley.my-ui-lib will run
kley publish --push --scripts
```

## 4. Implementation Plan

1. Add a `--scripts` flag to `publish`, `add`, `update`, and `install` commands.
2. Create `run_lifecycle_scripts()` that:
   a. Reads `package.json` from the target (consumer) project.
   b. Looks for `prekley` / `postkley` / `prekley.<pkg>` / `postkley.<pkg>`.
   c. Executes found scripts via the detected package manager (`npm run` / `yarn` / `pnpm`).
   d. Logs a warning on failure but continues the main operation.
3. Integrate into `run_update()` (used by `update` and `publish --push`) and into
   `add` / `install`.
4. Honor the f-24 `.kleyrc` default for the `--scripts` opt-in.

## 5. Acceptance Criteria

- `prekley` / `postkley` run in the consumer project during update/push when
  `--scripts` is passed.
- `prekley.<pkg>` / `postkley.<pkg>` run for the matching package.
- Execution order: general `prekley` → `prekley.<pkg>` → update →
  `postkley.<pkg>` → general `postkley`.
- Without `--scripts`, no consumer lifecycle scripts run — backward compatible.
- A failing consumer script logs a warning but does not abort the main operation.
- Scripts run via the project's detected package manager.
